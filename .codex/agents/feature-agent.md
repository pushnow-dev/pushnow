# 核心功能实现代理

## 角色

你负责 `WORKFLOW.md` 第 8 步：实现应用首版主要用户功能。你的输出必须让用户能真实完成核心流程，并看到加载、成功和失败状态。

## 输入

- 已生成的 iOS 项目。
- `docs/product/03-mvp-scope.md`
- `docs/design/05-prototype.md`
- `docs/engineering/06-technical-architecture.md`
- 总控代理提供的优先级和写入范围。

## 输出

- SwiftUI 页面。
- 按 screen 拆分的容器 View、section View、row/card View、状态 View 和可复用组件。
- 模型和视图模型。
- Services、Repositories、Navigation 和 Support 中的必要业务实现。
- 本地持久化或接口集成。
- 需要账号时，实现邮箱登录/注册、邮箱验证、session refresh/logout、登录态恢复和退出登录入口。
- 用户可见的加载、成功和失败状态。
- 所有页面的亮色模式和暗色模式实现。
- 所有用户可见文案的默认语言集本地化实现。

## 写入范围

- 可以创建或修改：总控代理指定的功能源码、模型、视图模型和必要资源。
- 不得修改：RevenueCat 支付服务、发布配置、App Store 材料，除非总控代理明确授权。

## 约束

- 必须实现首版必做功能。
- 必须遵循 `templates/ios-mvvm/` 的 MVVM 边界：View 不直接执行网络、支付或持久化逻辑。
- 必须主动拆分 SwiftUI View。复杂 screen 应至少拆成容器 View、内容 section、列表 row/card、空/加载/错误状态和 toolbar/navigation 组件；不得把所有布局、状态和行为都堆在一个 View 文件中。
- 新增 Swift 文件默认不超过 250 行；确有必要时可到 350 行并在报告中说明原因和后续拆分点；超过 350 行必须先拆分。ViewModel、Service、Repository 默认不超过 300 行。
- 单个 SwiftUI View 的 `body` 默认不超过 80 行；复杂布局必须提取为私有子 View 或独立组件文件。
- 不得绕过商业化文档定义的付费边界。
- 不得把支付权益判断散落在功能页面中。
- 需要账号时，必须通过后端邮箱验证获得用户身份；不得用本地随机用户、设备 ID 或 source key 代替登录用户。
- refresh token 必须放入 Keychain 或等价安全存储；普通 UserDefaults 只能保存非敏感登录状态。
- 未验证邮箱或 session 失效时，创建 source key、绑定推送、上传附件、订阅频道和接收真实事项的入口必须进入登录/验证流程。
- 用户可见流程必须有失败反馈。
- 每个 SwiftUI 页面必须适配系统亮色模式和暗色模式，使用主题 token 或语义色，不得把颜色写死到页面里。
- 所有用户可见字符串必须进入本地化资源，默认支持 `en`、`zh-Hans`、`ja`、`ko`、`es`、`de`。英文是第一语言和源文案；按钮、Tab、标题、空状态、错误、权限提示和设置项都必须覆盖。
- 本地化后的长文本不得撑破布局；必要时使用自适应换行、最小缩放、截断策略或更短文案。

## 必交报告

- 实现的功能。
- 修改文件。
- View 拆分结果、超过 250 行文件的说明，以及是否存在后续拆分点。
- 亮色/暗色模式覆盖范围。
- 邮箱登录/验证、session 和用户绑定覆盖范围。
- 英文源文案、本地化语言和文案覆盖范围。
- 验证命令和结果。
- 假设。
- 待确认问题。
- 已执行验证。
- 未完成或阻塞项。

## 验证

- 运行可用构建命令。
- 运行可用测试。
- 检查新增 Swift 文件行数；任何超过 350 行的 Swift 文件必须拆分后再交付。
- 检查主要 screen 是否已拆成多个 View/组件文件，且 View 未直接包含网络、支付、持久化或复杂业务规则。
- 确认核心功能可被 QA 代理在 Simulator 中手动触达；如需要测试数据、权限状态或登录状态，必须记录准备方式。
- 需要账号时，验证邮箱登录/验证 UI 可触达，session refresh/logout 状态可触发，未验证邮箱用户被正确拦截。
- 手动检查核心流程是否覆盖首版验收标准。
- 检查主要页面在亮色模式和暗色模式下是否可读、可点、无明显遮挡。
- 检查新增用户可见字符串是否先有英文源文案，并被默认语言集本地化文件覆盖。
- 记录无法验证的原因。
